RAG evaluation harness
======================

Install the eval dependency group first (not installed by a plain `uv sync`):

    uv sync --group eval


Running on a real corpus (read this first)
------------------------------------------

The numbers only mean something on a real document set. On a toy corpus (a
handful of chunks) every command still runs, but:

  - ann and rerank scores are identical — with few chunks there is nothing to
    reorder, so the cross-encoder comparison is degenerate.
  - precision@3/@5 are capped low because each question has ~1 relevant chunk.
  - answer_correctness (Ragas) is statement-F1 and swings wildly at small n.

So the numbers below are decisions only once the corpus is real. A sane target:

  1. Upload a representative document set to a tenant agent and let ingestion
     finish (Celery must be running: the upload queues process_document).
     Confirm chunks exist before building:

         python manage.py shell -c "from django_tenants.utils import schema_context; \
           schema_context('<tenant>').__enter__(); \
           from documents.models import DocumentChunk; print(DocumentChunk.objects.count())"

     Aim for at least a few hundred chunks across several documents. Below ~100
     chunks the ranking metrics stay in the degenerate regime above.

  2. Build a full golden set (the defaults total 70 questions):

         python manage.py build_golden_set --tenant <tenant> --agent <id> --sleep 2

     --sleep 2 stays under the Gemini free-tier rate limit. Then spot-check ~15
     records by hand (see the warning under section 1) before trusting anything.

  3. Run and score as in sections 2 and 3 below. Now the report answers real
     questions: does rerank beat ann, and what does the false-answer rate cost
     when you lower a threshold (see "Sweeping the thresholds").

Keep the golden set once it is good: comparing runs requires the SAME set.


1. Build a golden set from a tenant agent's own documents
---------------------------------------------------------

    python manage.py build_golden_set --tenant acme --agent 3

    --single-hop N      factual questions answerable from one chunk   (default 30)
    --multi-part N      questions needing two chunks                  (default 15)
    --negation N        "X apart from Y" exclusion questions          (default 10)
    --out-of-scope N    plausible but unanswerable questions          (default 15)
    --label-threshold F cross-encoder score at/above which a non-seed
                        chunk is labelled supporting evidence         (default 0.5)
    --sleep F           pause between generations to stay under the
                        Gemini free-tier rate limit                   (default 0)

Writes evaluation/dataset/golden_set.jsonl.

Spot-check ~15 records by hand before trusting any number that comes out of it.
If the summary reports close to 1.00 labels per in-scope query, label completion
found nothing beyond the seed chunks — lower --label-threshold and rebuild, or
Recall@k will be measured against an artificially sparse ground truth.

Do not delete the golden set casually: it is the only fixed reference point for
comparing runs, and a regenerated set is not comparable to the old one.

2. Run the pipeline against it
------------------------------

    python manage.py run_eval --tenant acme --agent 3

    --limit N       evaluate only the first N records (smoke runs)
    --keep-cache    do NOT disable the semantic cache (off by default:
                    with the cache on you measure the cache, not the pipeline)

Writes reports/report.json, reports/report.md and reports/eval_records.json.

3. Score answers with Ragas
---------------------------

    python manage.py score_ragas

    --limit N       samples to score (default 40 — Ragas costs 1-3 LLM calls
                    per metric per sample)
    --metrics ...   faithfulness,answer_correctness,context_precision,context_recall

Scores only records that produced a grounded answer (status "high"), then merges
the results into report.json and report.md.


What the metrics mean here
--------------------------

Ranking metrics are computed over the FULL pre-truncation candidate list, not the
chunks the user's answer was built from. `_score_and_select` returns at most 4
chunks (usually 2), so Recall@5 / nDCG@10 are undefined on the delivered set.

Both retrieval stages are reported: `ann` is the raw pgvector order, `rerank` is
after the cross-encoder. If rerank does not beat ann, the cross-encoder is not
earning its place on the critical path.

Precision@5 is capped at 0.2-0.6 when a query has only 1-3 relevant chunks. Read
Recall@k, nDCG and Precision@1 as the real signals.

Queries with no relevant chunks (the out-of-scope stratum) have UNDEFINED recall
and nDCG, not zero, and are excluded from those means. Every metric reports the
number of records that contributed.

correct_refusal_rate and false_answer_rate are what keep a threshold sweep
honest. Lowering TOP_SIMILARITY_THRESHOLD will always improve recall; the false
answer rate is what it costs.


Sweeping the thresholds
-----------------------

The point of all of the above. Edit the constants in
rag/processors/retriever.py:10-17, re-run run_eval against the SAME golden set,
and diff report.json. Recall and false-answer rate move in opposite directions.


Known bias
----------

Supporting labels are produced by the same cross-encoder the pipeline uses to
rerank, so retrieval metrics are mildly flattering to that reranker. Removing the
bias needs an LLM adjudication pass over every candidate chunk.
